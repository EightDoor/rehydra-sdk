# Design

## Goals / Non-Goals

**Goals:** 流式保存不得删除存储里已存在的条目。

**Non-Goals:** 不解决"两个写者从同一旧快照分配新 ID 撞号"的问题——那是分配策略
问题，合并层面无法补救（已发出的占位符不能再改号）。

## Decisions

### 保存前读最新并合并

`saveMergedToStorage()` 先 `load` 当前映射并解密，以流自身映射为准，只补充缺失的键。
代价是一次额外读取，发生在节流保存或流结束时，不在每个 chunk 上。

备选：流每处理一个 chunk 前重新载入映射。否决原因：per-chunk IO，且不能修复已经
发出的占位符。

### 解密失败不吞掉

密钥在流生命周期内被换掉时，解密会失败。这里直接抛给调用方，与普通脱敏的行为一致，
不静默退化成"只写流自己的映射"（那会删掉别人的条目）。

## Risks / Trade-offs

- [同类型并发分配仍会撞号] → 已在代码 `shortcut:` 注释与 spec 场景中写明；严格隔离需
  改为保存前统一分配 ID。
- [entityCounts 仍用流自身的统计] → 合并进来的条目不会计入本次写入的 entityCounts，
  与既有行为一致（原本也只统计流处理的实体）。
